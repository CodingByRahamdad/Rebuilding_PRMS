# DECISIONS.md

Currently approved architectural decisions for this migration. Recorded as of Phase 1. Any future session should check this file before proposing an alternative approach to one of these points.

1. PostgreSQL will replace MongoDB.
2. Frontend and backend will be separated into independently deployable applications.
3. Existing UI/UX must remain unchanged during migration (see `UI_UX_RULES.md` for the full preservation policy).
4. Frontend must remain database-agnostic (it should only ever talk to the backend's API, never assume MongoDB- or PostgreSQL-specific data shapes beyond what the API contract documents).
5. Existing API contracts should be preserved wherever practical (see `API_CONTRACTS.md` for the current baseline that any future contract change must be diffed against).
6. Migration will happen in controlled, explicitly-approved phases (see `MIGRATION_PLAN.md`).
7. MongoDB will not be removed until PostgreSQL is fully verified (Phase 13 is the last phase, gated on Phases 8–12 completing successfully).
8. Every phase requires a review before the next phase begins — no phase should be started as an unreviewed continuation of a previous one, including this documentation phase.

## Phase 4 decisions

15. **UUID primary keys** (`gen_random_uuid()`) for every proposed PostgreSQL table, with a nullable `legacy_mongo_id` column on each table for migration traceability back to the original Mongo `ObjectId`. Chosen over bigint/serial because the frontend and API already treat `id` as an opaque string end-to-end — UUIDs preserve that contract with zero API/frontend shape change. Confirmed with the project owner before finalizing the Phase 4 design (see `POSTGRESQL_SCHEMA.md`, `DATABASE_SCHEMA.md`).
16. **Embedded/`Mixed` array fields are normalized into real child tables**, not ported as `JSONB` columns. Applies to `Patient.prescriptions/reports/billingInvoices/medicalHistory` and `MedicalRecord.prescription/labResults/attachments`. Chosen to satisfy the explicit Phase 4 requirement to determine "the correct relational model" rather than defer that decision to a later phase; the alternative (JSONB) was considered and rejected as keeping the same weak, unqueryable guarantees the app has today. Confirmed with the project owner before finalizing the Phase 4 design. `Patient.vitals` (a single fixed-shape object, not a list) is the one exception — flattened into typed columns instead of a child table, since it isn't a repeating structure.
17. **Enums become `VARCHAR` + `CHECK` constraints**, not native Postgres `ENUM` types and not lookup/reference tables. Reasoning: native `ENUM` alteration (`ALTER TYPE`) is more disruptive than extending a `CHECK` clause, and none of the current enum-like value sets (role, status, shift, appointment type, etc.) have their own attributes that would justify a lookup table — they're small, static, code-defined sets today, matching how the app already treats them (Zod schemas in code, not a DB-managed type).
18. **`Appointment`/`MedicalRecord`/`Payment` → `Patient`/`Doctor` become real, nullable foreign keys** (`ON DELETE SET NULL`), each paired with a `legacy_*_ref TEXT` column that preserves the original loosely-typed Mongo value when it doesn't resolve to a real row. This replaces the current `Schema.Types.Mixed` fields (which include synthetic non-ObjectId placeholders like `PT-####`/`doc-###`) with enforced referential integrity, while still accommodating existing dirty data without rejecting any record. This is the largest structural change introduced by Phase 4 and the primary risk carried into Phase 7 (`MIGRATION_PLAN.md`).
19. **No `departments` table was created.** The current application has no backend Departments module or Mongoose collection — department data is frontend-only (`departmentService.ts`, localStorage). Creating a table now would invent a relationship the app doesn't have; left as an open question below, consistent with the existing "explicitly NOT yet made" entry on this same topic from Phase 1.
20. **Denormalized display-string relationships were kept as text columns, not converted to enforced FKs**: `patients.attending_doctor_name` (no `doctorId` on Patient today), `payments.service_name` (no `serviceId` on Payment today), `activity_logs.user_display` (no `userId` on ActivityLog today — though see the open question below for one deliberate, non-enforced exception added to `activity_logs`). Reasoning: the current app never establishes these as real relationships; adding FKs here would not reflect "the correct relational model" for *this* application's actual behavior, it would be inventing new behavior.
21. **`Nurse.assignedPatientIds` becomes a `nurse_patient_assignments` junction table.** Unlike the denormalized strings above, this one *is* a real existing many-to-many relationship in the app (a nurse has a list of assigned patient IDs) — it's just modeled as a raw string array today rather than a ref array or join table. Normalizing it is a faithful port, not an invented relationship.

## Open questions raised by Phase 4 — reviewed in a Phase 4 verification pass (2026-09-21)

A follow-up verification pass re-checked these six questions directly against repository/service/controller code (not just the Mongoose models). Two are now **RESOLVED** with direct code evidence; four remain **DEFERRED** (no code evidence was found that resolves them one way or the other, so the project owner's input is still required before Phase 7).

### RESOLVED

22. **Payment field drift — RESOLVED, no schema change.** `payments.validation.ts` (Zod) accepts, and `payments.service.ts` actively maps, `totalAmount`/`paidAmount`/`invoiceNo`/`invoiceNumber`/`insuranceProvider`/`claimId`/`serviceType`/`description` — but `payment.model.ts`'s Mongoose schema declares none of these fields and does not set `strict:false` (unlike `Patient`). Mongoose's default strict mode therefore **silently drops all of these extra fields** on every real-MongoDB save; they only actually persist in the in-memory demo fallback store (`memory-store.ts`), which is not real production persistence. **Decision: the proposed `payments` table stays exactly as designed (`amount`, `service_name` only)** — this is confirmed to be a faithful port of the *actual* current real-database behavior, not a design gap. Separately, this reveals a **pre-existing application bug**, unrelated to and not fixed by this schema phase: the frontend `PaymentTransaction` type (`frontend/src/types.ts`) expects `invoiceNo`/`paidAmount`/`insuranceProvider`/`claimId` to be present on every payment returned from the real API, but they are silently `undefined` today outside demo mode. Worth flagging to the project owner as an existing defect, independent of the Postgres migration.
23. **Dual-modeled prescriptions — RESOLVED as confirmed-independent, design unchanged.** Verified `patients.service.ts` and `medical-records.service.ts` are fully independent code paths with zero cross-reference between `Patient.prescriptions` and `MedicalRecord.prescription` anywhere in the backend. This confirms (rather than changes) the original design choice: the shared `prescriptions` table keeps both `patient_id` and `medical_record_id` as independent nullable parent FKs, since the code provides no basis for assuming the two lists represent the same clinical fact.

### DEFERRED (still require project-owner input before Phase 7)

24. **`bloodGroup` vs `bloodType`** on `patients`: no code evidence found favoring one over the other as canonical; both are near-duplicate default-`'O+'` fields with identical treatment throughout the codebase. Deferred.
25. **`invoices` (from `Patient.billingInvoices`) vs the standalone `payments` collection**: not re-investigated in the verification pass beyond the original Phase 4 finding — both represent a bill/charge against a patient from two different, currently-unlinked places in Mongo. Deferred.
26. **`activity_logs.user_id` — DEFERRED, with a more precise reason than originally stated.** Verified against `activity-logger.ts`: the calling code *does* receive `actor.id` at the point an activity log is written, but discards it into a formatted display string (`"${actor.name} (${actor.role})"`) before persisting — no code path today stores or looks up a raw user id from an activity log. The column is technically populatable in a future phase (the id is available at write time), but doing so requires an **application-code change** (capturing `actor.id` alongside the string), which is out of scope for a schema-design-only phase. Deferred to that future implementation phase, not decided here.
27. **`departments` table**: still no backend Departments module or collection exists (department is frontend-only, `departmentService.ts`/localStorage) — unchanged from the original Phase 4 finding, no new evidence either way. Deferred, same status as the pre-existing Phase 1 note on this topic.

## Corrections made during the Phase 4 verification pass (documentation only, no schema redesign)

28. **Table count corrected: 18, not 17.** The Phase 4 final report undercounted by one; `POSTGRESQL_SCHEMA.md` now states the authoritative list of all 18 tables at the top of the document.
29. **`nurse_patient_assignments` corrected to allow nullable `patient_id` plus a `legacy_patient_ref` column**, matching the pattern already used on `appointments`/`medical_records`/`payments`. The original design had both sides `NOT NULL`, which would have silently dropped any assignment whose `assignedPatientIds` string doesn't resolve to a real patient — verified this is a real, not hypothetical, situation (`nurses.repository.ts` demo data contains placeholder values like `'p-1'`, `'p-8'`).
30. **`receptionists` index description corrected**: `receptionist.model.ts` has no compound `schema.index()` call (only separate field-level indexes on `department` and `shift`) — the original draft incorrectly copied `nurses`' real compound `{department:1,shift:1}` index onto `receptionists` as well. Fixed to two separate single-column indexes.
31. **`services` was missing an explicit Indexes line** in the original draft; added (`name` unique, plus separate `category`/`department`/`is_available` indexes, matching `service.model.ts`'s field-level declarations — no compound index exists there either).
32. **`legacy_mongo_id` uniqueness rule stated more precisely**: `UNIQUE` on the 10 tables with a 1:1 Mongo source document (verified safe — MongoDB `ObjectId`s are globally unique by construction, no model overrides `_id`); will be `NULL` (not merely "non-unique") on the 8 tables normalized from array items, since those items never had a discrete Mongo id to begin with.
33. **`ON DELETE CASCADE` on `doctors/nurses/receptionists.user_id` clarified as a Postgres-side design choice, not a ported Mongo behavior** — MongoDB has no FK/cascade concept, and the current app only ever soft-deletes, so there was no existing behavior to match; this FK action only matters if a future phase introduces real hard deletes.
34. **API-contract preservation (task verification item 10) confirmed with code citations**: `patients.repository.ts`/`medical-records.repository.ts` do a single embedded-document read today with no aggregation logic; normalizing the embedded arrays into separate Postgres tables preserves the JSON response contract but will require new aggregation/re-nesting logic in the future Phase 6 backend implementation — documented explicitly in `DATABASE_SCHEMA.md` rather than left implicit.

## Phase 2 decisions

9. Backend and frontend each mirror their existing internal folder shape 1:1 under `backend/src/...` and `frontend/src/...` respectively, rather than reorganizing during the move — this keeps the relocation a pure move (verified via `git mv`, preserving history) with no internal import-path rewrites needed beyond the new roots.
10. Local-dev cross-origin requests are handled via a Vite `server.proxy` (forwarding `/api` and `/socket.io` to the backend) rather than making `apiClient.ts`/`socketClient.ts` always require an absolute backend URL. This keeps both files' request-building logic behaviorally unchanged in dev (still same-origin from the browser's perspective) and avoids needing to get cross-origin credentialed-cookie CORS exactly right for local development. Absolute URLs (`VITE_API_BASE_URL`, `VITE_SOCKET_URL`) are an opt-in production-only fallback.
11. **npm** was chosen over bun as the package manager for both new apps — the root repo had both `bun.lock` and `package-lock.json` with no other signal disambiguating which was authoritative; npm is the safer, more universally-available common denominator for CI/deploy environments.
12. `@google/genai` was removed from both new `package.json` files — confirmed unused by any code (paired with the also-unused `GEMINI_API_KEY` env var). A dependency removal is a state change worth recording even though it has zero runtime effect.
13. `backend/src/shared/data/mockData.ts` (and the types it needs) was duplicated from `frontend/src/data/mockData.ts` rather than extracted into a shared package — the backend's in-memory Mongo fallback store (`memory-store.ts`) depends on this data, and introducing a shared/workspace package was judged out of scope for a phase whose objective is architectural *separation*, not new shared tooling. The duplication is documented as a known drift risk in `MIGRATION_PROGRESS.md`.
14. A full Docker rework (two services, two Dockerfiles, container CORS/proxy wiring) was explicitly deferred to a future phase rather than attempted now — `docker-compose.yml` was already non-functional before Phase 2 (references a missing `Dockerfile`), so leaving it as-is does not regress anything, and a correct rework is a nontrivial redesign outside this phase's "smallest safe change" mandate.
